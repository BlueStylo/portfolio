P23 / AI 운영·사내 도구

머신러닝 웹 큐·운영 로드맵

P18의 nnU-Net 기반 CT segmentation 파이프라인을 사내 사용자가 직접 돌릴 수 있게 만든 DICOM ZIP 업로드, 큐, 진행률, 로그, STL 다운로드 중심의 내부 ML 웹 운영 화면.

2025-2026 위키 기록 공개 범위 제한
AI운영사내도구

Operations web product

P18의 모델을 사내 사용자가 직접 돌릴 수 있는 웹 제품으로 묶었습니다.

이 화면은 모델 자체보다 운영 흐름에 가까운 작업입니다. zip 업로드, 순차 처리 큐, 긴급 대기열, 진행률, 전체/개별 로그, STL 다운로드까지 한 화면에서 확인하도록 만들었습니다.

P18이 모델 선택과 CT segmentation 파이프라인의 이야기라면, 이 페이지는 그 결과를 사내 사용자가 계속 돌릴 수 있게 만든 웹 프로덕트 쪽 기록입니다.

입력 정책 1 zip = 1 case

사용자가 올리는 DICOM ZIP을 케이스 단위로 큐에 넣고 처리하도록 잡았습니다

큐 운영 순차 + 긴급 대기열

일반 작업은 순차 처리하고, 급한 케이스는 별도 대기열로 넣을 수 있게 했습니다

상태 추적 진행률 + job 로그

전체 상태와 선택 job 로그를 분리해서 어디까지 진행됐는지 바로 보이게 했습니다

산출물 STL download

skin, bone, airway 결과물을 작업 목록에서 바로 받을 수 있는 흐름으로 연결했습니다

Queue to artifact

업로드에서 STL 다운로드까지, 모델 주변의 운영 구간을 제품화했습니다.

실제 업무에서는 AI 결과가 만들어지는 순간보다 그 전후가 더 중요했습니다. 사용자가 무엇을 올렸는지, 지금 어디까지 진행됐는지, 실패하면 어느 단계에서 멈췄는지, 완료되면 어떤 파일을 받아야 하는지까지 화면 안에서 끝나야 했습니다.

01 Upload

DICOM ZIP을 올리고 1 case 단위로 작업을 생성합니다

02 Queue

순차 처리 또는 긴급 대기열로 job을 배치합니다

03 Inference

서버에서 NIfTI 변환, nnU-Net 추론, 후처리를 진행합니다

04 Artifact

mask 결과를 STL/thumbnail/log 산출물로 정리합니다

05 Download

완료된 결과를 사용자가 job 목록에서 바로 내려받습니다

개요

  • P18에서 만든 CT segmentation 파이프라인을 실제 사내 업무에서 쓰려면 모델 코드만으로는 부족했습니다. 누군가가 DICOM ZIP을 올리고, 처리 상태를 보고, 완료된 STL을 바로 받을 수 있어야 했습니다.
  • 그래서 이 항목은 nnU-Net 자체보다 그 모델을 사내에서 계속 돌릴 수 있게 만든 웹서비스 쪽 기록으로 보는 게 맞습니다. 모델 선택과 분할 품질은 P18, 업로드와 큐와 로그가 있는 운영 화면은 P23으로 나누는 구조가 더 깔끔합니다.
  • 제가 회사에서 유일한 개발자였기 때문에, 이 화면도 별도 프론트/백엔드 담당자 없이 서버 구성, 업로드 처리, 큐 관리, 로그 출력, 다운로드 흐름까지 직접 이어 붙여야 했습니다.

역할

모델 코드를 사내 웹서비스로 연결하기 위해 업로드 정책, 순차 처리 큐, 긴급 대기열, 진행률 표시, 전체/개별 로그, STL 다운로드 흐름을 한 화면에 묶었습니다. 서버 구성부터 백엔드, 프론트엔드, 운영 로그 설계까지 단독으로 처리했습니다.

문제

  • DICOM ZIP은 한 번 올라가면 처리 시간이 몇 분씩 걸리고, 여러 사용자가 동시에 올릴 수도 있습니다. 큐가 없으면 현재 무엇이 대기 중이고 무엇이 끝났는지 운영자가 바로 알기 어렵습니다.
  • 실패가 났을 때도 단순히 '실패'라고만 보이면 안 됐습니다. DICOM 변환, 추론, STL 변환, 임시 파일 정리 중 어디에서 문제가 생겼는지 로그를 바로 봐야 했습니다.
  • 완료된 결과는 설계자가 바로 받을 수 있어야 했기 때문에 job 목록 안에서 STL 다운로드까지 이어져야 했습니다.
  • 화면에는 실제 파일명과 병원/환자 단서가 섞일 수 있어서, 공개본에서는 이 부분을 민감정보 제거 기준으로 따로 분리했습니다.

내가 한 결정

  • 업로드 정책은 1 zip = 1 case 기준으로 두었습니다. 사용자가 파일을 올리면 대기열에 들어가고, 운영자가 긴급 작업을 따로 넣을 수 있게 했습니다.
  • 작업 상태는 전체, 대기, 실행중, 완료 숫자로 먼저 보이게 했습니다. 운영자가 화면을 열었을 때 지금 시스템이 바쁜지, 멈춰 있는지 바로 파악하는 게 중요했습니다.
  • 로그는 전체 로그와 선택 job 로그를 분리했습니다. 전체 로그는 시스템 상태를 보는 용도이고, job 로그는 특정 케이스에서 실제로 어떤 파일이 만들어졌는지 확인하는 용도입니다.
  • P18과 P23은 서로 연결하되 같은 항목으로 합치지 않는 쪽으로 정리했습니다. P18은 모델 선택과 CT-to-mesh 파이프라인의 대표 작업이고, P23은 그 결과를 사내 웹 제품으로 운영하기 위한 항목입니다.

과정

  • 상단에는 파일 선택과 업로드 버튼, 긴급 대기열 추가 버튼, 처리 정책을 배치했습니다. 사용자가 이 화면에서 어떤 입력을 넣을 수 있는지 먼저 보이게 했습니다.
  • 중간에는 전체 작업 수, 대기, 실행중, 완료 상태를 숫자로 보여주고, 아래 작업 목록에는 job id, 파일명, 상태, 진행률, 생성/종료 시간, STL 다운로드 버튼을 넣었습니다.
  • 하단에는 전체 로그와 선택한 job 로그를 나누어 두었습니다. 실제로 STL 변환이 끝났는지, 임시 디렉터리가 정리됐는지, thumbnail이 만들어졌는지를 화면에서 확인할 수 있게 했습니다.
  • P18 운영 대시보드가 누적 성과를 보는 화면이라면, 이 ML 웹 화면은 개별 job을 올리고 처리하는 작업 화면입니다. 두 화면을 연결하면 모델이 실제 업무에 어떻게 들어갔는지가 더 잘 보입니다.

검증

  • 완료된 job에서 STL 다운로드 가능 상태와 실제 처리 시간이 표시되는지 확인했습니다.
  • 선택한 job 로그에서 skin, bone, airway STL 생성과 임시 파일 정리 과정이 이어지는지 확인했습니다.
  • P18의 누적 운영 대시보드 수치와 이 화면의 job 단위 처리 기록이 서로 같은 운영 흐름에 속한다는 점을 확인했습니다.

결과

  • nnU-Net segmentation 결과를 사내 사용자가 직접 올리고 받을 수 있는 웹서비스 화면으로 연결했습니다.
  • 이 작업 덕분에 P18이 단순 모델 실험으로 보이지 않고, 실제 사용자가 접근하는 운영 제품까지 이어진다는 점을 보여줄 수 있습니다.
  • 운영 화면 기준으로는 업로드, 큐, 실행 상태, job 로그, 결과 다운로드가 한 흐름에 들어오면서 AI 파이프라인을 현장에서 반복 실행할 수 있는 형태가 되었습니다.
  • P18이 모델 선택과 CT-to-mesh 파이프라인이라면, 이 작업은 그 결과를 사내에서 직접 돌리는 웹 프로덕트로 이어 붙인 기록입니다.

증거

  • DICOM ZIP 업로드와 1 zip = 1 case 처리 정책
  • 순차 처리 큐, 긴급 대기열, 실시간 진행률, job별 로그 화면
  • 처리 완료 후 skin/bone/airway STL 다운로드 버튼과 임시 파일 정리 로그
  • 업로드부터 STL 다운로드까지 이어지는 실제 사내 시연 영상
  • P18 운영 대시보드의 746회 실행 기록과 연결되는 job 단위 운영 화면

보강할 근거 자료

  • 공개용으로 정리한 ML 웹 전체 화면
  • 업로드-큐-추론-STL 다운로드 흐름도
  • 권한/보존 기간/긴급 큐 정책 정리
  • 실패 케이스 대응 로그 예시

공개 기준

  • 공개 버전에서는 파일명, 병원명, 작업 로그, 내부 경로처럼 케이스를 추정할 수 있는 단서는 제거합니다.
  • job id, 생성/종료 시간, 다운로드 버튼, 로그 문구는 운영 구조를 보여주는 수준으로만 남기고 실제 케이스 단서는 제외합니다.
