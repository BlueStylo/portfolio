P23 / AI 운영 / 사내 도구

CT 분할 웹 큐와 운영 화면

의료 3D AI 파이프라인의 nnU-Net 기반 CT 분할을 설계팀이 직접 돌릴 수 있게 만든 사내 웹 서비스입니다. DICOM ZIP 업로드, 처리 큐, 진행률, 로그, STL 다운로드를 한 화면에 묶었습니다.

2025-2026
CTDICOMsegmentationnnU-NetSTL웹 서비스큐사내 도구AI운영

Operations web product

CT 분할 모델을 설계팀이 직접 돌리는 사내 웹 서비스로 묶었습니다.

의료 3D AI 파이프라인의 모델을 설계팀이 개발자 없이 돌릴 수 있게, zip 업로드, 순차 처리 큐, 긴급 대기열, 진행률, 전체와 개별 로그, STL 다운로드를 한 화면에 모았습니다. 여기서 받은 STL은 보형물 설계 자동화 도구의 입력으로 들어갑니다.

입력 정책 1 zip = 1 case

사용자가 올리는 DICOM ZIP을 케이스 단위로 큐에 넣고 처리하도록 잡았습니다

큐 운영 순차 + 긴급 대기열

일반 작업은 순차 처리하고, 급한 케이스는 별도 대기열로 넣을 수 있게 했습니다

상태 추적 진행률 + job 로그

전체 상태와 선택 job 로그를 분리해서 어디까지 진행됐는지 바로 보이게 했습니다

산출물 STL download

skin, bone, airway 결과물을 작업 목록에서 바로 받을 수 있는 흐름으로 연결했습니다

Queue to artifact

업로드에서 STL 다운로드까지, 모델 주변의 운영 구간을 제품화했습니다.

실제 업무에서는 AI 결과가 만들어지는 순간보다 그 전후가 더 중요했습니다. 사용자가 무엇을 올렸는지, 지금 어디까지 진행됐는지, 실패하면 어느 단계에서 멈췄는지, 완료되면 어떤 파일을 받아야 하는지까지 화면 안에서 끝나야 했습니다.

01 Upload

DICOM ZIP을 올리고 1 case 단위로 작업을 생성합니다

02 Queue

순차 처리 또는 긴급 대기열로 job을 배치합니다

03 Inference

서버에서 NIfTI 변환, nnU-Net 추론, 후처리를 진행합니다

04 Artifact

mask 결과를 STL/thumbnail/log 산출물로 정리합니다

05 Download

완료된 결과를 사용자가 job 목록에서 바로 내려받습니다

개요 역할 문제 결정 과정 검증 결과 근거 자료

개요

  • 의료 3D AI 파이프라인에서 만든 CT 분할 파이프라인을 실제 사내 업무에서 쓰려면 모델 코드만으로는 부족했습니다. 누군가가 DICOM ZIP을 올리고, 처리 상태를 보고, 완료된 STL을 바로 받을 수 있어야 했습니다.
  • 모델을 만든 제가 운영 화면까지 만들어야 설계팀이 개발자 없이 매일 돌릴 수 있다고 봤습니다.
  • 연구소의 유일한 개발 인력이라, 이 화면도 별도 프론트엔드와 백엔드 담당자 없이 서버 구성, 업로드 처리, 큐 관리, 로그 출력, 다운로드 흐름까지 직접 이어 붙였습니다.

역할

모델 코드를 사내 웹서비스로 연결하기 위해 업로드 정책, 순차 처리 큐, 긴급 대기열, 진행률 표시, 전체와 개별 로그, STL 다운로드 흐름을 한 화면에 묶었습니다. 서버 구성부터 백엔드, 프론트엔드, 운영 로그 설계까지 단독으로 처리했습니다.

문제

  • DICOM ZIP은 한 번 올라가면 처리 시간이 몇 분씩 걸리고, 여러 사용자가 동시에 올릴 수도 있습니다. 큐가 없으면 현재 무엇이 대기 중이고 무엇이 끝났는지 운영자가 바로 알기 어렵습니다.
  • 실패가 났을 때 '실패' 표시만으로는 부족했습니다. DICOM 변환, 추론, STL 변환, 임시 파일 삭제 가운데 어디에서 문제가 생겼는지 로그로 바로 봐야 했습니다.
  • 완료된 결과는 설계자가 바로 받을 수 있어야 했기 때문에 job 목록 안에서 STL 다운로드까지 이어져야 했습니다.

내가 한 결정

  • 업로드 정책은 1 zip = 1 case 기준으로 두었습니다. 사용자가 파일을 올리면 대기열에 들어가고, 운영자가 긴급 작업을 따로 넣을 수 있게 했습니다.
  • 작업 상태는 전체, 대기, 실행중, 완료 숫자로 먼저 보이게 했습니다. 운영자가 화면을 열었을 때 지금 시스템이 바쁜지, 멈춰 있는지 바로 파악하는 게 중요했습니다.
  • 로그는 전체 로그와 선택 job 로그를 분리했습니다. 전체 로그는 시스템 상태를 보는 용도이고, job 로그는 특정 케이스에서 실제로 어떤 파일이 만들어졌는지 확인하는 용도입니다.

과정

  • 상단에는 파일 선택과 업로드 버튼, 긴급 대기열 추가 버튼, 처리 정책을 배치했습니다. 사용자가 이 화면에서 어떤 입력을 넣을 수 있는지 먼저 보이게 했습니다.
  • 중간에는 전체 작업 수, 대기, 실행중, 완료 상태를 숫자로 보여주고, 아래 작업 목록에는 job id, 파일명, 상태, 진행률, 생성/종료 시간, STL 다운로드 버튼을 넣었습니다.
  • 하단에는 전체 로그와 선택한 job 로그를 나누어 두었습니다. 실제로 STL 변환이 끝났는지, 임시 디렉터리가 정리됐는지, thumbnail이 만들어졌는지를 화면에서 확인할 수 있게 했습니다.

검증

  • 완료된 job에서 STL 다운로드 가능 상태와 실제 처리 시간이 표시되는지 확인했습니다.
  • 선택한 job 로그에서 skin, bone, airway STL 생성과 임시 파일 정리 과정이 이어지는지 확인했습니다.

결과

  • 2026년 9월까지 이 화면으로 1,228건 작업을 실행했습니다(2026.09.21 대시보드). 작업 완료율은 99.1%(완료/(완료+실패))이고, 자동 처리 구간 평균은 7.4분입니다. 여기서 나온 뼈와 피부 STL은 보형물 설계 자동화 도구의 입력으로 바로 들어갑니다.
  • 2026년 6월부터 9월 21일까지 실행한 745건은 모두 완료됐습니다. 단계별 평균은 DICOM 변환 0.5분, 5-fold 추론 6.1분, STL 변환 0.7분이고, 지금까지 입력 391.47GB와 산출 STL 91.55GB를 사내 GPU 서버에서 처리했습니다.
  • 서버 이전이나 모델 교체처럼 끝나는 시간이 불확실한 변경은 별도 개발 서버에 같은 서비스를 먼저 띄워 함께 돌린 뒤 넘겼습니다.
  • 운영 화면 기준으로는 업로드, 큐, 실행 상태, job 로그, 결과 다운로드가 한 흐름에 들어오면서 AI 파이프라인을 현장에서 반복 실행할 수 있는 형태가 되었습니다.
  • 비개발 직군인 설계팀이 직접 CT를 올리고 STL을 받아 바로 설계에 들어갑니다.

근거 자료

  • DICOM ZIP 업로드와 1 zip = 1 case 처리 정책
  • 순차 처리 큐, 긴급 대기열, 실시간 진행률, job별 로그 화면
  • 처리 완료 후 skin/bone/airway STL 다운로드 버튼과 임시 파일 정리 로그
  • 업로드부터 STL 다운로드까지 이어지는 실제 사내 시연 영상
  • 2026년 9월 기준 1,228건 작업 실행 기록과 이어지는 job 단위 운영 화면
