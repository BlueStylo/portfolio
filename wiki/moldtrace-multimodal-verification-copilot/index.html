P33 / 산업 AI·검증

MoldTrace 멀티모달 검증 코파일럿

제조 컨펌 스레드에서 수집 계정 멘션이 감지되면 n8n이 전체 대화와 몰드 이미지·PDF를 읽기 전용으로 수집·별칭화하고, self-hosted Gemma 4(31B)가 단 한 번의 멀티모달 호출로 수주·라벨·몰드 각인을 대조해 격리된 검토 채널에 검증 리포트를 남기는 human-in-the-loop 검증 코파일럿입니다. 합성 채널 라이브 데모의 MISMATCH 검출과 실제 운영 수주 스레드 30건의 Shadow Review 전체 왕복을 거쳐, 2026.07부터 담당자가 실제 업무에서 쓰고 있습니다.

Industrial AI verification evidence

실채널 데모와 검증 리포트가 그대로 공개 근거입니다.

합성 데이터 기반 개발 테스트 채널에서 봇 멘션부터 검증 리포트 게시까지의 전체 왕복을 기록했습니다. 이후 시스템은 운영 채널을 읽기 전용으로 수집하는 Shadow Review와 확인 방식 열이 추가된 6열 리포트로 확장됐습니다.

개요

  • 의료용 보형물 제조에서는 한 수주 건이 Mattermost 스레드 하나로 진행됩니다. 최상단 수주정보 아래로 설계·수정 대화가 이어지고, 라벨 텍스트와 몰드 렌더 이미지가 첨부된 컨펌 요청이 올라오면 담당자가 눈으로 대조한 뒤 확인 댓글을 남깁니다.
  • 한 글자 차이가 다른 환자의 제품이 되는 도메인이라, 이 시스템의 최우선 지표는 전체 정확도가 아니라 잘못된 것을 통과시키지 않는 false acceptance 경계입니다.
  • 검증 대상인 몰드 자체가 P19 설계 자동화 엔진이 생성하는 산출물입니다. 도메인과 생성 로직을 모두 아는 상태에서 검증 시스템을 설계했습니다.

역할

실무 관찰로 오류 모델 12유형과 검사 매트릭스를 구조화한 뒤, Python 검증 API(Bearer 인증·strict 스키마·PDF 전 페이지 변환·fail-closed·자동 테스트 69개), 6열 리포트 프롬프트 계약, n8n Shadow Review 워크플로(24노드), 비식별 관측성(JSONL·토큰 사용량·고정 오류 코드)까지 단독 설계·구현했습니다. 결정론 baseline → 2단계 LLM/VLM → one-shot 멀티모달 → 실데이터 Shadow Review로 구조를 직접 진화시키며 실패 지점을 줄였습니다.

문제

  • 접수와 컨펌 요청 사이에 비정형 수정 대화가 끼어들어 기준값이 바뀝니다. 규칙 기반 파서는 형식이 유지될 때만 강했고, 문맥 해석이 필요한 순간 깨졌습니다.
  • 이미지가 콜라주 한 장일 수도, 여러 장 분할 업로드일 수도, 같은 몰드의 다른 시점 사진일 수도 있어 고정된 이미지 파이프라인을 만들기 어려웠습니다.
  • 반대로 모델에게 전부 맡기고 통제가 없으면 잘못된 출력이 그대로 게시됩니다. 판단의 유연성과 운영의 통제를 어디서 나눌지가 핵심 설계 문제였습니다.

내가 한 결정

  • 구조를 세 번 바꿨습니다. 결정론 baseline은 합성 390건 평가에서 false acceptance 0/360을 기록하며 오류 모델을 구조화했지만 비정형 대화에 무력했고, Thread Interpreter → Visual Judge 2단계 구조는 실연동 경로를 검증했지만 단계 사이 파싱 오류와 문맥 손실이 생겼습니다. 최종적으로 전체 스레드와 모든 이미지를 Gemma에 정확히 한 번 전달하는 one-shot 구조로 단순화했습니다.
  • 책임을 셋으로 나눴습니다. n8n은 수집·P/I/D 별칭화·멱등성·게시만, Python은 인증·계약·무결성·fail-closed만, Gemma는 업무 판단과 최종 리포트 작성만 담당합니다. Python이 주문번호를 다시 비교하거나 모델 판단을 재해석하지 않습니다.
  • 실데이터 검증은 Shadow Review로 확장했습니다. 운영 수주 채널은 수집 전용 계정으로 GET만 수행하고, 결과는 원본 스레드가 아니라 격리된 개발 검토 채널에 새 글로만 게시해 운영 채널을 절대 변경하지 않습니다. source와 게시 credential도 분리했습니다.
  • Ollama가 pattern, uniqueItems 같은 복잡한 JSON Schema 제약에서 연결을 끊는 문제를 재현하고, 모델에는 기본 타입·필수 필드만 주고 세부 무결성은 Python에서 검사하도록 스키마 강제 위치를 분리했습니다.
  • MATCH도 승인이 아닙니다. 모든 리포트에 사람 최종확인 문구를 정확히 한 번 강제하고, 최종 컨펌 권한은 담당자에게 남겼습니다.

과정

  • n8n Shadow Review 워크플로(24노드, Code 노드 11개)가 수집 계정 멘션을 감지해 운영 스레드와 원본 이미지·PDF를 읽기 전용으로 수집하고, 실제 Mattermost ID를 P001/I001/D001 별칭으로 치환해 Python API에 전달합니다. 실제 ID와 토큰은 n8n 밖으로 나가지 않습니다.
  • Python이 Bearer 인증, strict 스키마, Base64/MIME/크기, 참조 무결성을 검사하고 PDF는 전 페이지를 이미지로 변환한 뒤, 원문과 모든 시각 자료를 Gemma /api/chat 한 번에 전달합니다. 시각 자료가 없으면 모델을 호출하지 않고 REVIEW_REQUIRED로 종료합니다.
  • Gemma가 verdict(MATCH/MISMATCH/REVIEW_REQUIRED), 사용한 P/I/D 근거, D번호 제목·검토 범위·확인 방식 열이 포함된 6열 한국어 Markdown 리포트를 직접 작성하고, Python이 최소 출력 계약을 검증해 footer를 붙인 뒤 n8n이 격리된 검토 채널에 새 글로 게시합니다.
  • trigger ledger 기반 멱등 처리로 같은 멘션의 중복 처리·게시를 차단하고, 게시 결과가 불명확하면 자동 재게시하지 않습니다.
  • 비식별 JSONL 진단이 단계·상태·PDF 페이지 수·Ollama 토큰 사용량을 고정 오류 코드로 기록합니다. 원문·개인정보·이미지 Base64는 기록 항목에서 구조적으로 제외됩니다.

검증

  • 실제 운영 수주 스레드 30건에서 Shadow Review 전체 왕복(읽기 전용 수집 → 단일 Gemma 분석 → 격리 개발 채널 게시)을 확인했습니다. 운영 원본 채널로 향하는 POST 경로는 존재하지 않습니다.
  • 합성 채널 라이브 데모에서 멘션 → 수집 → API → GPU 추론(RTX PRO 6000, 사용률 약 97%) → MISMATCH 리포트 게시까지 전체 왕복을 영상으로 기록했습니다 (당시 5열 프롬프트 기준의 역사 데모).
  • 자동 테스트 69개로 요청당 호출 1회, 이미지·PDF 페이지 순서 보존, unknown/중복 참조 거부, fail-closed, footer 1회, 멘션 중립화, 로그 비유출을 고정했습니다. 모델 정확도 테스트가 아니라 계약·안전 경계 테스트라는 점을 구분해서 남깁니다.
  • 실제 Gemma 스모크에서 합성 기준값과 다른 몰드 각인의 불일치를 MISMATCH로 검출했고, 합성 2페이지 PDF 실추론에서 D001 근거 반환을 확인했습니다. 아직 정성적 사례 수준이며, 원본 몰드 데이터셋 기반 유형별 회귀 평가와 FAR 측정이 다음 게이트입니다.

결과

  • AI가 사람의 컨펌을 대신하는 게 아니라, 담당자가 원본을 확인하기 전에 불일치를 먼저 찾아주는 verification copilot으로 실채널에서 동작하는 working vertical slice를 확보했습니다.
  • 모델 성능과 시스템 안정성을 구분하는 평가 태도, 실패에서 배운 구조 단순화, 프라이버시 익명화 경계까지 산업 AI 시스템 설계 역량의 근거로 이어집니다.
  • 결정론 baseline에서 실데이터 Shadow Review 30건 왕복까지를 거쳐 2026.07부터 담당자가 실제 업무에서 쓰고 있습니다. 이 기록은 여기까지의 여정을 담습니다.
  • Phase 2로는 사람이 검증한 오류 사례만 candidate → human verified → indexed 절차로 인덱싱하는 Visual Case Memory와 Hybrid Retrieval을 계획하고 있습니다.

증거

  • 사내 Shadow Review E2E: 실제 운영 수주 스레드 30건에서 읽기 전용 수집 → 단일 Gemma 분석 → 격리 개발 채널 새 글 게시까지 전체 왕복 확인 (운영 원본 채널로 향하는 POST 없음)
  • 라이브 데모 영상: 합성 채널에서 봇 멘션 후 약 20여 초 만에 MISMATCH 리포트 게시 — 당시 5열 프롬프트 기준의 역사 데모 (현행 계약은 확인 방식 열이 추가된 6열)
  • Python 단위·계약·PDF 렌더링·관측성·HTTP 통합 테스트 69개 — 요청당 호출 1회, fail-closed, footer 1회, 멘션 중립화, 로그 비유출 고정
  • 결정론 PoC-0 baseline: 합성 390건(정상 30 + 오류 12유형×30)에서 false acceptance 0/360 — 규칙 기반 합성 평가
  • P/I/D 참조 별칭화 경계 — 실제 Mattermost ID·토큰이 Python과 모델까지 전달되지 않음을 테스트로 보증

보강할 근거 자료

  • 담당자 실사용 개시 (2026.07) — 현장 피드백과 사례를 쌓는 중
  • 원본 몰드 데이터셋 기반 유형별 Gemma 회귀 평가와 FAR 측정
  • Visual Case Memory + Hybrid Retrieval (Phase 2, candidate → human verified → indexed)

공개 기준

  • 공개 자료는 전부 합성 데이터입니다. 병원·환자·주문번호는 가상 값이며, 실제 수주 정보는 어떤 자산에도 포함하지 않습니다.
  • 데모 영상과 GIF는 내부망 개발 테스트 채널 녹화본으로, 프레임 전수 검수와 소유자 확인 후 공개했습니다. 서버 자격증명과 실제 Mattermost ID는 노출되지 않습니다.
  • 사내 실데이터 Shadow Review의 원문·화면·식별자는 공개 자료에 포함하지 않습니다.
