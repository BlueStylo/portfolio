MoldTrace 제조 컨펌 검증

제조 컨펌 스레드에서 봇을 멘션하면 n8n이 스레드 전체와 몰드 이미지, PDF를 읽기 전용으로 모읍니다. 사내 GPU의 로컬 멀티모달 모델(Gemma 4 31B)이 요청당 한 번의 호출로 대화와 라벨, 이미지를 함께 읽고 판정과 근거가 달린 확인 표를 씁니다. Python은 판단하지 않고 인증, 입력 계약, 참조 무결성, 출력 계약 검사를 맡으며, 처리에 실패하거나 응답이 계약을 어기면 결과를 내보내지 않고 사람 검토로 넘깁니다(fail-closed). 최종 컨펌은 담당자가 하고, 2026.07부터 사내에서 쓰이고 있습니다.

Industrial AI verification

사내에서 돌아가는 검증봇, 멘션부터 리포트 게시까지.

2026.07부터 사내에서 운영하는 시스템을 합성 데이터 테스트 채널에서 녹화했습니다. 데모는 초기 리포트 형식이고, 지금은 운영 채널을 읽기 전용으로 수집하고, 확인 방식 열을 더한 6열 리포트를 씁니다.

개요

  • 의료용 보형물 제조에서는 한 수주 건이 Mattermost 스레드 하나로 진행됩니다. 최상단 수주정보 아래로 설계와 수정 대화가 이어지고, 라벨 텍스트와 몰드 렌더 이미지가 첨부된 컨펌 요청이 올라오면 담당자가 눈으로 대조한 뒤 확인 댓글을 남깁니다.
  • 한 글자 차이가 다른 환자의 제품이 되는 도메인이라, 이 시스템에서 가장 먼저 지키는 지표는 잘못된 것을 통과시키지 않는 false acceptance입니다.
  • 검증 대상인 몰드는 제가 만든 보형물 설계 자동화 도구가 생성한 산출물입니다. 도메인과 생성 로직을 모두 아는 상태에서 검증 시스템을 설계했습니다.

역할

실무 관찰로 오류 모델 12유형과 검사 매트릭스를 구조화해 초기 규칙 PoC를 만들었고, 지금 쓰는 Python 검증 API(Bearer 인증, strict 스키마, PDF 전 페이지 변환, 출력 계약 검사, fail-closed, 자동 테스트), 6열 리포트 프롬프트 계약, n8n 수집과 게시 워크플로(24노드), 비식별 관측성(JSONL, 토큰 사용량, 고정 오류 코드)까지 단독으로 설계하고 구현했습니다. 규칙 PoC로 오류 모델을 먼저 세우고, 2단계 모델 구조에서 파싱 오류와 문맥 손실을 겪은 뒤 모델 호출을 한 번으로 줄였습니다.

문제

  • 접수와 컨펌 요청 사이에 비정형 수정 대화가 끼어들어 기준값이 바뀝니다. 규칙 기반 파서는 형식이 유지될 때만 강했고, 문맥 해석이 필요한 순간 깨졌습니다.
  • 이미지가 콜라주 한 장일 수도, 여러 장 분할 업로드일 수도, 같은 몰드의 다른 시점 사진일 수도 있어 고정된 이미지 파이프라인을 만들기 어려웠습니다.
  • 반대로 모델에게 전부 맡기고 통제가 없으면 잘못된 출력이 그대로 게시됩니다. 판단의 유연성과 운영의 통제를 어디서 나눌지가 핵심 설계 문제였습니다.

내가 한 결정

  • 구조는 세 단계를 거쳤습니다. 처음에는 오류 12유형을 구조화하고 검사 7종을 규칙 5종과 모델 2종으로 나눈 PoC를 만들었습니다. 이 초기 규칙 기준선을 합성 390건으로 평가했을 때 false acceptance는 0/360이었습니다. 그런데 실제 수주 스레드는 비정형이고 정정이 대화 중간에 섞여 있어 고정 필드 파싱이 맞지 않았습니다. 그다음 대화 해석과 이미지 판정을 두 모델 단계(Thread Interpreter, Visual Judge)로 나눴더니 중간 결과를 넘기는 과정에서 파싱 오류와 문맥 손실이 생겼습니다. 지금은 스레드 전체와 모든 시각 자료를 모델에 한 번에 보내 종합 판단하게 하고, 코드는 판단 대신 안전 경계를 맡습니다.
  • 역할을 셋으로 나눴습니다. Gemma는 최신 정정을 포함한 대화 맥락, 수주정보와 라벨, 이미지와 PDF의 각인을 함께 읽고 MATCH, MISMATCH, REVIEW_REQUIRED 판정과 근거 참조, 확인 표를 씁니다. 판독이 불확실하거나 근거가 부족하면 추측하지 않고 REVIEW_REQUIRED로 사람에게 넘깁니다. Python은 판단하지 않고 인증, 입력 계약, P/I/D 참조 무결성, 출력 계약 검사, fail-closed만 맡습니다. 주문번호나 환자명을 Python이 다시 파싱하거나 비교하지 않습니다. n8n은 수집, P/I/D 별칭화, 멱등성, 게시만 담당합니다.
  • 실데이터 검증은 Shadow Review로 시작했습니다. 원본 수주 채널은 수집 전용 계정으로 GET만 수행하고, 결과는 원본 스레드가 아니라 격리된 개발 검토 채널에 새 글로만 게시해 원본 채널을 바꾸지 않았습니다. source와 게시 credential도 분리했습니다.
  • Ollama가 pattern, uniqueItems 같은 복잡한 JSON Schema 제약에서 연결을 끊는 문제를 재현하고, 모델에는 기본 타입과 필수 필드만 주고 세부 무결성은 Python에서 검사하도록 스키마 강제 위치를 나눴습니다.
  • MATCH도 승인이 아닙니다. 모든 리포트에 사람 최종확인 문구를 한 번씩 붙이고, 최종 컨펌 권한은 담당자에게 남겼습니다.

과정

  • n8n 워크플로(24노드, Code 노드 11개)가 수집 계정 멘션을 감지해 스레드 전체와 원본 이미지, PDF를 읽기 전용으로 수집하고, 실제 Mattermost ID를 P001/I001/D001 별칭으로 치환해 Python API에 전달합니다. 실제 ID와 토큰은 n8n 밖으로 나가지 않습니다.
  • Python이 Bearer 인증, strict 스키마, Base64, MIME, 크기, 참조 무결성을 검사합니다. PDF는 전 페이지를 이미지로 변환한 뒤, 스레드 전체와 모든 시각 자료를 Gemma /api/chat 한 번에 전달합니다. 시각 자료가 없으면 모델을 호출하지 않고 REVIEW_REQUIRED로 종료합니다.
  • Gemma가 verdict(MATCH, MISMATCH, REVIEW_REQUIRED), 사용한 P/I/D 근거, D번호 제목, 검토 범위, 확인 방식 열이 들어간 6열 한국어 Markdown 리포트를 작성하면, Python이 출력 계약과 참조 무결성을 검사하고 멘션을 중립화한 뒤 사람 최종확인 footer를 한 번 붙이며, n8n이 리포트를 게시합니다.
  • trigger ledger 기반 멱등 처리로 같은 멘션의 중복 처리와 게시를 막고, 게시 결과가 불명확하면 자동 재게시하지 않습니다.
  • 비식별 JSONL 진단이 단계, 상태, PDF 페이지 수, Ollama 토큰 사용량을 고정 오류 코드로 기록합니다. 원문, 개인정보, 이미지 Base64는 기록 항목에서 구조적으로 빠집니다.

검증

  • 실제 수주 스레드에서 멘션 한 번으로 수집, 모델 분석, 게시까지 전체 왕복을 확인했습니다. 원본 수주 채널은 읽기 전용으로 수집했습니다.
  • 합성 채널 라이브 데모에서 멘션, 수집, API 호출, GPU 추론(RTX PRO 6000, 사용률 약 97%), MISMATCH 리포트 게시까지 전체 왕복을 영상으로 기록했습니다.
  • 계약과 안전 경계 자동 테스트로 요청당 호출 1회, 이미지와 PDF 페이지 순서 보존, unknown과 중복 참조 거부, fail-closed, footer 1회, 멘션 중립화, 로그 비유출을 고정했습니다.
  • 실제 Gemma 스모크에서 합성 기준값과 다른 몰드 각인의 불일치를 MISMATCH로 검출했고, 합성 2페이지 PDF 실추론에서 D001 근거 반환을 확인했습니다.

결과

  • 2026.07부터 사내에서 쓰이고 있습니다. 담당자가 원본을 확인하기 전에 불일치를 먼저 찾아 주는 검증 보조 도구이고, 테스트 채널 dry-run과 실제 수주 스레드의 전체 왕복 확인을 거쳐 사내 운영으로 넘겼습니다.
  • false acceptance를 최우선 지표로 둔 평가 설계, 실패에서 배운 구조 단순화, 프라이버시 경계까지 산업 AI 시스템을 설계부터 운영까지 직접 맡았습니다.

근거 자료

  • 실데이터 E2E: 실제 수주 스레드에서 멘션 한 번으로 수집, 모델 분석, 게시까지 전체 왕복 확인
  • 라이브 데모 영상: 합성 채널에서 봇 멘션 후 20초 남짓 만에 MISMATCH 리포트 게시
  • Python 단위, 계약, PDF 렌더링, 관측성, HTTP 통합 테스트로 요청당 호출 1회, fail-closed, footer 1회, 멘션 중립화, 로그 비유출 고정
  • 초기 규칙 기준선의 합성 평가(PoC): 정상 30건과 오류 12유형 각 30건, 총 390건에서 false acceptance 0/360
  • P/I/D 참조 별칭화 경계: 실제 Mattermost ID와 토큰이 Python과 모델까지 전달되지 않음을 테스트로 확인
