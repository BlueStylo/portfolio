Model decision

최신 모델보다, 매일 돌릴 수 있는 모델이 필요했습니다.

2D TransUNet의 경우 추론 속도가 빠르고 학습 비용이 낮았지만, 최종 3D 메쉬로 변환 시 해상도 저하 및 슬라이스 간 단절이 발생하여 의료용 정밀도 스펙을 만족하지 못했습니다. 또한 3D TransUNet과 U-Mamba는 단일 GPU VRAM 요구 조건, 학습 난이도, 추론 시간까지 함께 보면 실제 서비스 도입에 무리가 있었습니다. 따라서 최신 트렌드를 무리하게 적용하기보다, 분할 품질의 일관성과 프로덕션 환경의 확장성을 담보할 수 있는 nnU-Net v2의 파인튜닝을 선택했습니다.

AI infrastructure

모델 실험을 하려면, 먼저 계속 돌릴 수 있는 서버가 필요했습니다.

이 서버는 단순히 CT segmentation 학습 검증만을 위한 장비가 아니었습니다. 일부 3D Transformer 계열은 단일 GPU 40GB 이상 VRAM이 필요했고, 멀티 GPU로 VRAM을 합치는 방식이 전제되지 않았습니다. 그래서 RTX PRO 6000 96GB 서버 도입을 제안했고, 내부 LLM 모델 튜닝과 여러 AI 서비스 실험까지 고려해 Linux 기반 학습/추론 환경을 직접 구성했습니다.

도입 배경 single GPU VRAM

3D TransUNet 계열은 단일 GPU 40GB 이상 VRAM을 요구하는 경우가 있었고, 멀티 GPU로 VRAM을 단순히 합쳐 해결하는 구조가 아니었습니다.

기존 한계 5060 Ti / RTX 3090

회사에서 바로 쓸 수 있던 GPU는 5060 Ti였고, 초기에는 개인 RTX 3090으로 학습을 돌리며 한계를 확인했습니다.

서버 구성 RTX PRO 6000 96GB

이 조건 때문에 RTX PRO 6000 96GB 서버 도입을 제안했고, Linux/CUDA/PyTorch 기반 학습 환경을 구성했습니다.

확장 목적 CT + LLM base

이 서버는 CT 학습 검증뿐 아니라 내부 LLM 튜닝과 AI 서비스 실험을 위한 기초 자원 역할도 했습니다.

Operational evidence

746회 실행하며 평균 처리시간을 7.5분까지 낮췄습니다.

1 fold만 돌린 실험실 조건에서는 1분 미만도 나왔지만, 실제 서비스 흐름에서는 전처리, 5-fold 반복 추론, 후처리까지 모두 포함해서 봐야 했습니다.

Dataset preparation

모델보다 먼저, 학습 가능한 데이터셋을 만들어야 했습니다.

이 작업에서 가장 오래 걸린 부분은 모델 학습 자체보다 약 150건의 CT 케이스를 nnU-Net이 읽을 수 있는 형태로 정리하는 일이었습니다. 내부 세그멘테이션 프로그램은 구식이라 지원하지 않는 포맷이 많았고, 결국 부위별 흑백 라벨 이미지를 다시 3D label volume으로 합치는 과정이 필요했습니다.

training source ~150 CT cases

내부 작업 데이터 중 학습에 사용할 수 있는 케이스를 선별하고 다시 가공했습니다.

legacy tool 내부 세그멘테이션

지원 포맷이 제한적이라 바로 학습 데이터로 넘기기 어려웠습니다.

grayscale labels 부위별 흑백 export

skin, bone, airway, 기삽입 라벨을 각각 이미지로 분리했습니다.

volume rebuild 2D label -> nii.gz

slice 순서와 CT 기준을 맞춰 3D 학습 label volume으로 다시 합쳤습니다.

train ready nnU-Net dataset

모델이 읽을 수 있는 입력 CT와 multi-label mask 구조로 정리했습니다.

Label normalization

작업자마다 달랐던 라벨을 하나의 규칙으로 다시 맞췄습니다.

제가 오기 전부터 진행된 데이터가 섞여 있었기 때문에, 라벨 이름이 케이스마다 다르거나 아예 빠진 경우도 있었습니다. 먼저 라벨이 있는 케이스와 없는 케이스를 나누고, 이름 규칙이 다른 라벨은 Python으로 최대한 분리한 뒤, 자동으로 처리되지 않는 케이스는 다시 확인했습니다.

raw condition 라벨 있음 / 없음 / 이름 다름

기존 작업자마다 저장 방식이 달라서 파일만 보고 바로 학습 데이터로 묶을 수 없었습니다.

sorting pass Python 기반 1차 분류

폴더명, 파일명, 이미지 채널, 라벨 후보를 기준으로 자동 정리 가능한 케이스를 먼저 걸렀습니다.

manual repair 누락 케이스 수동 보정

라벨이 없거나 애매한 케이스는 직접 확인해서 다시 라벨링하고 학습 대상에서 쓸 수 있게 맞췄습니다.

Model comparison

최신 구조를 테스트했지만, 운영 기준은 달랐습니다.

2D TransUNet, 3D TransUNet, U-Mamba, Swin-Unet을 실제로 테스트하면서 단순히 새 모델인지보다 결과 해상도, 단일 GPU VRAM 조건, 추론 시간, 학습 반복 가능성, 유지보수 난이도를 같이 봤습니다. 결론적으로 제 환경에서는 nnU-Net v2를 파인튜닝하는 쪽이 가장 현실적이었습니다.

2D TransUNet 빠르지만 3D 품질이 부족했습니다.

학습과 추론은 가벼웠지만 512x512 resize 기반 결과가 목표 해상도에 닿지 못했습니다.

3D TransUNet 구조는 좋지만 운영 부담이 컸습니다.

일부 실험은 단일 GPU 40GB 이상 VRAM 조건부터 맞춰야 했고, 출력 해상도와 학습 난이도, 추론 시간을 함께 보면 실제 운영 후보로는 부담이 있었습니다.

U-Mamba 테스트했지만 충분히 빠르지 않았습니다.

새로운 구조의 장점은 있었지만, 현재 서버와 유지보수 조건에서는 선택지가 되기 어려웠습니다.

Swin-Unet 함께 검증했지만 최종 후보로 남지 않았습니다.

transformer 계열 비교군에 포함해 테스트했고, 품질·운영 조건을 종합하면 nnU-Net v2 파인튜닝이 더 현실적이라고 판단했습니다.

nnU-Net v2 충분한 품질과 운영 가능성의 균형이 맞았습니다.

최신은 아니지만 파인튜닝, 재현성, 추론 시간, 후처리 연결까지 고려하면 가장 현실적인 선택이었습니다.

CT-to-mesh pipeline

좌표를 잃지 않고 mask에서 mesh/STL까지 이어지게 만들었습니다.

의료용 3D 데이터는 일반적인 화면 좌표처럼 다루면 쉽게 틀어집니다. DICOM에서 NIfTI로 넘어갈 때 spacing, orientation, slice order를 보존해야 했고, LPS 좌표계를 설계자가 쓰기 쉬운 world 기준으로 변환하는 후처리도 필요했습니다.

01 DICOM -> 기준 nii.gz

원본 CT의 spacing과 orientation을 먼저 확보했습니다.

02 label volume 정렬

흑백 라벨 이미지를 CT 기준 slice와 맞춰 multi-label volume으로 합쳤습니다.

03 nnU-Net v2 inference

파인튜닝된 모델로 skin, bone, airway, prosthesis mask를 추론했습니다.

04 LPS -> design world

의료 좌표계를 실제 설계 검토가 쉬운 방향과 위치로 보정했습니다.

05 mesh / STL / preview

후처리된 산출물을 부위별 mesh와 검토 가능한 STL로 정리했습니다.

Public-safe version

공개본에는 구조와 판단만 남기고, 민감한 원본은 걷어냅니다.

실제 환자 CT, 병원명, 내부 서버 주소, 원본 파일명은 공개하지 않습니다. 대신 민감정보를 제거한 비교 영상, 산출물 보드, 운영 대시보드, 좌표/mesh 파이프라인 도식처럼 작업의 판단과 구조를 설명할 수 있는 근거만 남깁니다.

Related web product
